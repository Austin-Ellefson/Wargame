# Terrain bridge

The bridge reads the Godot battle export and prepares aligned input data for
**Combat Mission: Black Sea** map creation through the separate CMAutoEditor tool.
It runs alongside the Godot project; there is no plugin to install in Godot.

## Windows: first run

1. Install Python **3.11 or 3.12** from https://www.python.org/downloads/windows/.
   Include its launcher or add Python to PATH. Python 3.12 was used for validation.
2. Download the repository's `phase-2-terrain-bridge` branch and extract it.
3. Double-click `setup_terrain_bridge.cmd` in the project root. It creates a
   local `.venv` and installs the bridge requirements.
4. Trigger a battle contact in your Godot game if you have not already.
5. Double-click `run_terrain_bridge.cmd`. It selects the newest Godot export.
   Choose **P** for an offline plan or **F** to fetch actual OSM and elevation data.
6. Open `terrain_output\T003_B2\preview.html` for the two-turn demo, then read
   `CMAUTOEDITOR.md` in the same folder for the manual CMBS editor handoff.

The launcher rebuilds generated files for that battle. Unrelated files such as
your notes or CMBS scenarios are retained. Rerun surface conversion after a
rebuild rather than reusing an old `terrain.csv`.

To choose a specific export, drag its JSON file onto `run_terrain_bridge.cmd`,
or use this command from the project folder:

```bat
run_terrain_bridge.cmd "%APPDATA%\Godot\app_userdata\Ukraine Wargame\battle_exports\T003_B2.json"
```

To try the bridge without launching Godot, use the checked-in demo export:

```bat
.venv\Scripts\python.exe -m terrain_bridge terrain_bridge\fixtures\battle_demo.json
```

`battle_demo.json` was generated by the actual Godot campaign loop, using
fictional formations and its placeholder central Ukraine test area.

## CLI: any supported Python desktop

Run from the repository root. Install dependencies once:

```bash
python -m pip install -r terrain_bridge/requirements.txt
```

| Task | Command |
| --- | --- |
| Offline plan | `python -m terrain_bridge battle.json` |
| Fetch both public sources | `python -m terrain_bridge battle.json --fetch` |
| Use local sources, no downloads | `python -m terrain_bridge battle.json --osm area.geojson --dem elevation.tif` |
| Fetch only missing source | `python -m terrain_bridge battle.json --osm area.geojson --fetch-dem` |
| Use multiple DEM tiles | `python -m terrain_bridge battle.json --dem west.tif --dem east.tif` |
| Read latest Godot export | `python -m terrain_bridge --latest --fetch` |
| Rebuild a package | Add `--overwrite` to the chosen command. |
| Choose another output parent | Add `--output path/to/folder`. |

Exit code 0 means the requested plan or preparation completed. **It does not
mean a playable CMBS scenario exists.** Exit code 1 means a requested data
source failed, with an incomplete manifest retained. Exit code 2 means invalid
arguments, input, dependency, or filesystem access. Read each source's status.

## Package contents

Files appear under `terrain_output/<battle_id>/`:

| File | Purpose |
| --- | --- |
| `manifest.json` | Dimensions, projected CRS, center alignment, source status/provenance, datum offset, external tool arguments. |
| `battlefield.geojson` | WGS84 outline of the actual projected tactical square. |
| `overpass_query.txt` | Request for public roads, buildings, land use, water, rail, and other features. |
| `osm_raw.json` | Original Overpass response when fetched. |
| `osm.geojson` | WGS84 feature geometries and tags, ready for `osm2cm`. |
| `dem_8m.tif` | Complete projected 8 m elevation grid, preserving source elevation in meters. |
| `elevations.csv` | CMAutoEditor `x,y,z` elevation rows; southwest origin, x eastward, y northward. |
| `preview.png`, `preview.html` | Elevation-color map and geographic feature outlines for inspection. |
| `CMAUTOEDITOR.md` | Commands and manual editor steps for this battle's bounds. |
| `ATTRIBUTION.txt` | Source notices and links; keep with redistributed source-derived outputs. |

Offline plans leave OSM and DEM **pending** and do not write invented elevation
or feature files. `prepared` means both source inputs are ready. The manifest
always reports the CMBS scenario as **not_created** until a later integration
can verify otherwise. Local files are described as user-supplied, not as verified
public downloads.

## Alignment and fidelity

- The battlefield uses a locally selected WGS84 UTM projection. A 2 km side is
  2,000 projected meters, producing exactly 250 by 250 cells at 8 m spacing.
  This is not 2 km obtained by treating latitude/longitude degrees as meters.
- The southwest origin is snapped to the 8 m grid; its center shifts at most
  4 m in each projected axis. Requested and aligned centers are both recorded.
- The exact same projected bounds go to the OSM converter. Raster rows are
  reversed when writing CSV so the north/south orientation matches its grid.
- Elevation CSV values are rounded to meters with a **constant vertical offset**
  to bring the lowest terrain close to 20 m. Relief is preserved; source absolute
  altitude remains in the GeoTIFF. The bridge's CSV range is 20..999 m.
- The default source is Copernicus **GLO-30 Public, 2021 release**. It is a roughly
  30 m surface model and includes vegetation and structures. An 8 m resampling
  does not add 8 m detail or remove tree/building effects. For better ground
  fidelity, supply a suitable local terrain model.
- OSM can be incomplete or out of date. The query includes a small margin around
  the tactical square; objects with no mapped nodes nearby may still be absent.
  Building geometry, bridges, and terrain tiles still need checking in CMBS.
- Grid north differs slightly from true north. The test's campaign sector center
  remains a placeholder; the bridge does not model a real sub-sector contact.

## Data sources and failures

OSM is requested explicitly through Overpass. Full geometry and tags are
converted using `osm2geojson`; multipolygon handling is delegated to that
library. A timeout/remark response is rejected rather than accepted as partial
terrain. Keep OSM attribution and licensing information with derived data.

Copernicus tiles come from the public AWS bucket described at:
https://copernicus-dem-30m.s3.amazonaws.com/readme.html

The bridge first tries GDAL's efficient COG reader. If that reader cannot access
the tile, Python downloads it through verified HTTPS and caches the complete
original under `terrain_output/.dem_cache/`. First download can be tens of MB
per one-degree tile. Later maps in that tile reuse the cache. Downloads are
bounded to 256 MiB per tile; incomplete transfers are not cached. Failed access
never disables TLS checks or substitutes flat/fake terrain.

If a cached tile becomes corrupted, remove its generated cache file and retry,
or provide a local covering GeoTIFF. A local DEM must have one band, a CRS,
complete coverage, and heights in meters. Missing vertical units are assumed to
be meters and recorded; verify this before importing. NoData holes, wrong-area
sources, and incompatible height units are rejected.

For supplied feature data, use WGS84 GeoJSON with OSM tags in `properties` or
`properties.tags`. Legacy CRS overrides and wrong-area files are rejected.

## CMAutoEditor compatibility

Source inspected: https://github.com/DerButschi/CMAutoEditor/tree/c219c67c9cd8c3dd1bff0eaf3d2e49687082cf70

Verified contracts: `osm2cm` accepts `-i`, `-c`, `-o`, `-p black_sea`, and `-b EPSG
left bottom right top`; its terrain grid uses 8 m cells. `cmautoeditor` reads
CSV columns `x,y,z`, selects `black_sea`, and supports `--start-size-from-file`.
The bridge writes elevation CSV directly, avoiding differing crop sizes in the
upstream GeoTIFF converter. It does not vendor or execute upstream code.

The actual Windows editor automation, UI calibration, final map dimensions,
force setup, scenario launch, and battle-result import remain manual or future
work. Binary releases can differ from inspected source; check their `--help`
before following the generated handoff commands.

## Tests

```bash
python -m pip install pytest
python -m pytest -q tests/test_terrain_bridge.py
godot --headless --path . --script res://tests/campaign_smoke.gd
```

GIS tests use clearly synthetic rasters, and mocked network responses. They
cover real coordinate reprojection, CSV orientation, complete coverage, errors,
offline status, output preservation, HTTP fallback, and cache reuse. Live public
downloads are a separate integration check; automated tests never need network.
